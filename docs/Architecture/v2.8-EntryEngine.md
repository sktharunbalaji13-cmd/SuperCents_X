# Entry Engine — v2.8 Architecture

## Why a Validator Pipeline?

The legacy entry system embedded qualification logic inside the Confluence Engine and
ExecutionPlanner — direction checks, spread gating, session filtering, and risk limits
were scattered across multiple subsystems with no single point of validation.

The Entry Engine introduces a linear, composable validator pipeline:

```
Market Data → Confluence Engine → EntryOrchestrator → EntryDecision
                                       │
                                Validator Registry
                                       │
                          ┌────────────┼────────────┐
                          ▼            ▼            ▼
                    Direction    Confluence      Spread
                    Validator    Validator      Validator
                          │            │            │
                          └────────────┼────────────┘
                                       ▼
                               EntryFilterResult
                                  (PASS|WARN|FAIL)
```

Each validator implements `IEntryValidator` and is responsible for exactly one concern.
The pipeline short-circuits on the first `FILTER_FAIL`; warnings accumulate.

## Shadow Mode

Shadow mode runs both the legacy and new pipelines concurrently without letting the new
engine execute trades. This enables:

- **Behavioral comparison** — every confluence event is evaluated by both paths and the
  decisions are logged side by side
- **Risk-free validation** — no capital at risk while tuning thresholds
- **Quantitative gating** — the entry mode can graduate from `SHADOW` to `NEW` only after
  meeting measurable agreement/stability targets

### Three Entry Modes

| Mode | Legacy Runs | New Engine Runs | New Executes | Use Case |
|------|-------------|-----------------|--------------|----------|
| `LEGACY` | Yes | No | No | Production default |
| `SHADOW` | Yes | Yes | No | Validation, calibration |
| `NEW` | Yes | Yes | Yes | Future — after calibration |

`ENTRY_MODE_NEW` currently prints a one-time warning and falls back to `SHADOW`.

## Migration Strategy

1. **Implement** — build validators, registry, orchestrator behind `LEGACY` default
2. **Validate** — run in `SHADOW`, collect 3000+ comparisons, verify direction agreement
3. **Calibrate** — tune thresholds using empirical disagreement data
4. **Replace stubs** — swap `CShadowTradeStateProvider` / `CShadowRiskEvaluator` with live
   implementations
5. **Promote** — enable `ENTRY_MODE_NEW` when shadow telemetry meets acceptance criteria

## Centralized Telemetry

Shadow comparison data flows through a single path:

```
SymbolContext::Update()
    ↓
EntryOrchestrator::RecordShadowComparison()
    ↓
  • increments m_shadowTotal
  • increments m_shadowAgreements (if decisionMatch)
  • logs ShadowComparison struct
    ↓
EntryOrchestrator::Shutdown()
    ↓
  • prints summary: total, agreements, agreement %
```

This ensures no comparison is missed and the shutdown summary reflects every event.

## Retiring the Legacy Path

The legacy path should remain until:

- `ENTRY_MODE_NEW` has run in production for N trades (TBD)
- Decision agreement stabilises at ≥95%
- Direction agreement remains at ≥99%
- Zero shadow log failures or unexpected rejects
- No memory growth or performance regression

At that point the legacy execution path can be removed and the pipeline simplified.
